# DORA 低显存复现阶段技术报告

## 1. 项目目标

本项目尝试复现 DORA 的方向级测试时资源分配机制，并回答两个问题：

1. 在单张 8 GB 消费级 GPU 上能否运行 Policy、7B PRM 和语义嵌入模型组成的逐步搜索流程？
2. 4-bit PRM 是否仍能保持与 BF16 PRM 相近的候选排序与资源分配结果？

当前工作聚焦工程可行性和机制正确性，不把小样本结果外推为论文级准确率结论。

## 3. 低显存设计

三个模型不同时驻留 GPU，而是拆成独立进程：

```text
Policy 生成部分路径
        ↓ JSONL
PRM 对每个推理步骤评分
        ↓ JSONL
BGE 计算候选方向相似性并分配预算
        ↓ JSONL
复制父路径并继续下一轮生成
```

该结构允许每一阶段独立失败、检查和重跑，也让峰值显存由最大单模型阶段决定。

官方源码引用了仓库中不存在的 `configuration_qwen2_rm.py`。本地将其替换为 Transformers 4.47.1 中等价的 `Qwen2Config`，修复后相关搜索和奖励模型模块可正常导入。

## 4. 阶段结果

### 4.1 模型资源测量

| 模型与精度 | 状态 | 峰值GPU显存 | 峰值RAM | 示例推理耗时 |
|---|---|---:|---:|---:|
| Policy FP16 | 成功 | 2.89 GiB | 3.64 GiB | 1.25秒/64 tokens |
| BGE-M3 FP16 | 成功 | 1.07 GiB | 4.05 GiB | 0.41秒/2文本 |
| PRM CPU BF16 | 成功 | 0 | 12.92 GiB | 205.84秒/2步骤 |
| PRM CPU/GPU BF16 | 成功 | 6.01 GiB | 14.46 GiB | 1.48秒/2步骤 |
| PRM 4-bit NF4 | 成功 | 4.43 GiB | 4.57 GiB | 0.32秒/2步骤 |
| PRM GPU BF16 | OOM | 失败时7.32 GiB | — | 未完成 |
| PRM 8-bit mixed | OOM | 失败时7.24 GiB | — | 未完成 |

结论：4-bit NF4 是本机最实用路线；混合 BF16 可作为小规模保真对照。

### 4.2 单题端到端验证

在直角坐标转极坐标题目上生成 4 条候选，PRM 最后一步分数为：

```text
[0.7539, 1.0, 1.0, 1.0]
```

DORA 预算分配为 `[0, 1, 1, 2]`，最终加权答案为 `(3, π/2)`，判定正确。该题的候选都已完成，因此按早停规则未继续扩展。

### 4.3 五题初步对照

固定相同的 5 题 × 4 rollout，再切换选择或分配方法：

| 方法 | 正确率 |
|---|---:|
| Self-Consistency | 2/5 |
| 均匀 rollout + PRM 加权票 | 2/5 |
| DORA，仅质量分配 | 2/5 |
| DORA + BGE，alpha=0.01 | 2/5 |
| DORA + BGE，alpha=0.1 | 2/5 |
| DORA + BGE，alpha=1.0 | 2/5 |

这组结果仅用于验证公平的数据链和暴露工程问题。样本过小，不支持方法比较结论。

### 4.4 可靠答案评估

固定 10 道题、每题 4 条候选，共 40 条。人工标注候选实际表达的最终答案，并与改进后的自动抽取结果比较：

| 类型 | 数量 |
|---|---:|
| 正确 | 23 |
| 推理错误 | 5 |
| 截断且无最终答案 | 12 |
| 自动抽取与人工标注一致 | 40/40 |

该规则是在同一批样本上开发和验收，应在独立留出集继续检查泛化能力。

### 4.5 真正的逐步 DORA

以总预算 4 运行三轮“部分生成—评分—多样性—分配”，得到：

```text
round 0: [1, 2, 0, 1]
round 1: [1, 1, 1, 1]
round 2: [2, 0, 1, 1]
```

验收脚本确认：

- 每轮分配总和均为 4；
- 至少两轮为非均匀分配；
- 多 rollout 父路径被真实复制；
- 子路径完整继承父文本，并继续生成不同后缀。

最终 4 条路径中，2 条有可抽取答案但错误，另 2 条在 768 token 处截断。该实验验收的是搜索机制，不是任务准确率。

### 4.6 4-bit PRM 保真检查

对相同的 40 条冻结候选，只改变 PRM 加载精度：

| 指标 | 结果 |
|---|---:|
| Pearson | 0.9958 |
| Spearman | 0.9883 |
| 组内两两排序一致率 | 95% |
| 严格 Top-1 一致率 | 100% |
| 整数资源分配一致率 | 100% |

当前样本支持后续本地实验使用 4-bit PRM 进行资源分配，但不能证明其在所有数据与预算下都等价于 BF16。

## 5. 已发现的问题

1. 小 Policy 不总是遵循 boxed 输出协议，旧提取器会把 `π/2` 错取为 `2`。
2. 预算只有 4 时，BGE 产生的连续差异可能被整数舍入完全抹平。
3. PRM 分数接近 0/1 饱和时，固定质量温度会压倒多样性项。
4. 40 条候选有 12 条截断，Policy 与 token 预算是当前准确率的重要瓶颈。
5. 完整答案上的事后分配不能替代部分推理路径上的动态资源分配。

## 6. 结论边界

可以声称：

- DORA 核心逐步资源分配机制已在 8 GB GPU 上真实运行；
- 分时流水线可以把三个模型的峰值显存控制在 4.43 GiB 左右；
- 当前 40 条候选上，4-bit PRM 与混合 BF16 的排序和分配高度一致；
- 已形成可核验、可重复运行的阶段性工程成果。

不能声称：

- 已完整复现论文的 MATH-500/AIME 准确率；
- 当前实验已经证明 DORA 优于 REBASE、Beam Search 或 Self-Consistency；
- 4-bit PRM 在未知数据和全部预算上与 BF16 完全等价。

## 7. 低成本下一步

无需立即租用大规模 GPU，可优先完成：

1. 使用独立的 40–100 条候选作为答案解析留出集；
2. 实现跨轮累计的最大剩余分配，减少小预算舍入损失；
3. 根据 PRM 分数熵自适应设置质量温度；
4. 在本地 20–50 题上报告失败案例、截断率和分配变化；
5. 获得课题组反馈或算力支持后，再进行 MATH-500 正式对照。
